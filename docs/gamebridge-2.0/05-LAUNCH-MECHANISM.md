# Launch mechanism for `.gamebridge` Shortcuts

Research date: 2026-11-21 UTC. Scope: how LaunchBox for Android should hand a GameBridge-authored `.gamebridge` Shortcut to GameBridge so GameBridge can Dispatch it. This is a design comparison, not an implementation, and no device was used. Read with [LaunchBox integration](03-LAUNCHBOX-INTEGRATION.md), [Android platform evidence](ANDROID-PLATFORM-EVIDENCE.md), [export formats and folders](04-EXPORT-FORMATS-AND-FOLDERS.md), and the [glossary](../../GLOSSARY.md). The `.gamebridge` extension is a 2.0 proposal. It does not exist in the current Storefront table ([Shortcut.kt](../../core/src/main/kotlin/com/allourmedia/gamebridge/core/Shortcut.kt)).

## Verdict

**Keep option (a): the existing Custom Emulator (With Code) Setup command, with BridgeActivity branching on the extension.** In practice that means `-n <appId>/com.allourmedia.gamebridge.BridgeActivity -a com.allourmedia.gamebridge.action.DISPATCH -d {file.uri}`, set as the platform default, and a `.gamebridge` branch next to the `.art` one. It is the only route of the five that LaunchBox documents and the project has seen work. It keeps one exported entry point and one Setup command per platform, and it already matches the Android 13+ receiver filter rules. Treat it as conditional until the gates in [What must be verified on-device](#what-must-be-verified-on-device) pass. The main risk is that `{file.uri}` can be `file://`, and nothing documented guarantees `content://` with a read grant.

## Evidence classification

Same labels as [doc 03](03-LAUNCHBOX-INTEGRATION.md#evidence-classification):

- **Official documentation**: LaunchBox-owned help, changelog, or Android developer pages, read directly on the research date. A documented interface is not a runtime guarantee.
- **Historical observation**: a dated project record of device behaviour or a maintainer or user report. It was not reproduced in this research.
- **Repository fact**: what the current project files say.
- **Inference / unknown**: a hypothesis or design implication, or evidence that is missing.

## Project facts and observations

- **Repository fact:** [AndroidManifest](../../app/src/main/AndroidManifest.xml) exports `BridgeActivity` with one filter: action `com.allourmedia.gamebridge.action.DISPATCH`, category `DEFAULT`, scheme `content`. [`triageIntent`](../../core/src/main/kotlin/com/allourmedia/gamebridge/core/BridgeFailure.kt) rejects any other action (`WrongAction`) and any scheme other than `content` (`NotContentUri`). [BridgeActivity](../../app/src/main/kotlin/com/allourmedia/gamebridge/BridgeActivity.kt) already branches on the display-name extension: `.art` goes to Artemis, and the Local Shortcut extensions go through `interpretShortcut`. GameBridge targets SDK 36 with minimum SDK 30, and holds no storage permission.
- **Historical observation:** LaunchBox started `BridgeActivity` with the DISPATCH action, a `content://` URI and flags `0x10000001` (NEW_TASK plus GRANT_READ_URI_PERMISSION). Both Epic and Artemis picks did this ([investigation log](../investigation-log.md), 2026-11-02 and the Artemis entry). The setup was platform-wide on Windows: `DefaultEmulator` = `Custom Emulator (With Code)`, and per-game `EmulatorOverride` was empty. LaunchBox holds a SAF tree grant on `Games/pc` ([auto-import research](../research/launchbox-auto-import.md)). The device was an AYN Odin 2 Portal, recorded as Android 13 and LaunchBox 1.23.
- **Historical observation:** the G1 temporary game had a "Startup Uri File (Scoped Storage)" field set to `(None)`, next to a filesystem Startup File ([G1 report](../gamebridge-g1-launchbox-test-report-20261102.md)). The built-in GameNative entry failed on Shortcuts with "ROM file … could not be found" ([setup guide](../launchbox-setup.md)).

| Option | What LaunchBox documents | URI and grant | Android 13–16 | Player setup | Security surface | Unverified |
|---|---|---|---|---|---|---|
| **(a) Current command and extension branch** | The full syntax: `-n`, `-a`, `-d {file.uri}` (official). | Only `content://` with a read grant works, and that has been observed on one device. A `file://` value fails explicitly as `NotContentUri`, which is correct behaviour, not a bug. | **Official:** on Android 13+, a receiver targeting 33+ gets external intents only if they match its filter's action and categories ([intents and filters](https://developer.android.com/guide/components/intents-filters)). The DISPATCH action and the `DEFAULT` filter already satisfy this. Android 16 strict matching is **opt-in by the receiver** (`intentMatchingFlags="enforceIntentFilter"`, [behaviour changes 16](https://developer.android.com/about/versions/16/behavior-changes-16#safer-intents)). If it is enabled later, the action, category, scheme and MIME must all match. A MIME type set by LaunchBox would not match the current filter. | One Setup command per platform, unchanged. `.gamebridge` files need no new step if they sit on a platform that already uses the command. | One exported activity, as today. Any app can send the explicit intent, so input stays untrusted and validated. | Whether `{file.uri}` is `content://` without scoped storage set, or on a platform with no tree grant. Whether `.gamebridge` survives in `DISPLAY_NAME`. Behaviour on 14–16 and on other LaunchBox versions. |
| **(b) New action or activity for `.gamebridge`** | Same syntax as (a). | Same as (a). | Same rules as (a), on a second component. | **Worse.** LaunchBox has one command per platform, and nothing documents routing per extension. A second command only helps if `.gamebridge` files live on their own platform, or each game gets a per-game override. | A second exported entry point to keep validating. | The same items as (a). No benefit is documented. |
| **(c) Implicit `ACTION_VIEW` with a MIME or extension filter and a default-app association** | **Not documented.** LaunchBox documents no "open with default app" mode and no per-extension association. The closest is a custom command without `-n`, which is undocumented. | **Official:** for a `content:` URI, the type is inferred from the provider ([intents and filters](https://developer.android.com/guide/components/intents-filters)), and the filter must then list that MIME type. An unknown `.gamebridge` extension would most likely resolve to a generic type (inference). `pathPattern` only applies when `scheme` and `host` are set ([`<data>`](https://developer.android.com/guide/topics/manifest/data-element)). SAF document URIs encode the path in the document ID, so matching on the extension is fragile (inference). | Implicit resolution needs `CATEGORY_DEFAULT` and may show a chooser. Results depend on the provider and the OEM resolver. | High. A chooser or a "set as default" step, which may differ by device. | Broad. GameBridge would be offered for a generic MIME type in every file manager, so it receives arbitrary files. A VIEW intent from LaunchBox is also indistinguishable from one sent by any other app. | All of it. Whether LaunchBox can emit it at all, what type it sets, and how it resolves. |
| **(d) Per-game command or built-in emulator entry** | Per-game override: documented (official). Built-in GameNative or Winlator entries: documented, but they target those apps. | A per-game override uses the same placeholders as (a). The built-in entries do not reach GameBridge. | Same as (a) for a per-game command. | Per-game commands need a step for **every** game. That is the G1 path and the one that drifted ([doc 03](03-LAUNCHBOX-INTEGRATION.md)). Built-in entries are not applicable, and the GameNative one failed on Shortcuts. | Same as (a). | Precedence when both are set, and whether bulk editing exists. |
| **(e) Other placeholders or extras** (`{file.path}`, `--es`) | Only `{file.path}` and the `-e`/`--es`/`--ez` extras are documented. `{file.name}` is not. | `{file.path}` is a filesystem path. GameBridge holds no storage permission, and AGENTS.md forbids broad storage. **Official:** sending `file://` URIs across apps triggers `FileUriExposedException` for senders targeting 24+ ([Android 7.0 changes](https://developer.android.com/about/versions/nougat/android-7.0-changes#sharing-files)). An extra carries no grant. | A path is unreadable without all-files access. | Same as (a). | It adds untrusted strings and paths that must never be logged. | Nothing worth verifying. It contradicts project rules. |

## Recommendation

Use **(a)**. Add `.gamebridge` as a new extension branch inside `BridgeActivity` and `:core`, the same way `.art` was added, behind the existing DISPATCH action and `content` filter. Make no change to the Setup command, the exported surface or the manifest filter. Do not add a VIEW or MIME filter, a second activity, `{file.path}`, or extras. The setup guide should tell players to set the platform's Scoped Storage Permission to the folder that holds the Shortcuts, because the documented `{file.uri}` may otherwise be `file://`. This is an inference to confirm on a device.

A `.gamebridge` Shortcut must also be importable by LaunchBox and land on a platform that uses the Setup command. Storing it next to the existing `Games/pc` Shortcuts covers both. Where GameBridge writes the file is a separate decision, covered in [doc 04](04-EXPORT-FORMATS-AND-FOLDERS.md).

## What must be verified on-device

Each step needs the approvals in [AGENTS.md](../../AGENTS.md). Temporary Shortcut copies and LaunchBox configuration changes need explicit approval and a configuration backup first. Never record Shortcut contents or device paths.

1. With the platform's Scoped Storage Permission **set**, picking a temporary `.gamebridge` copy delivers the DISPATCH action, a `content://` URI, and a grant flag that includes `FLAG_GRANT_READ_URI_PERMISSION`. Capture this with debug `logcat` and `dumpsys activity`, not the saved XML.
2. With the permission **unset**, record what `{file.uri}` becomes. A `file://` value must produce the explicit `NotContentUri` dialog with no Dispatch.
3. `OpenableColumns.DISPLAY_NAME` on that URI ends in `.gamebridge`, including upper-case variants, and the read succeeds within the size cap.
4. Import: LaunchBox imports a `.gamebridge` file on the Windows platform, through Import Games or Add Game, with any extension filter configured as needed.
5. Repeat steps 1–3 on Android 14, 15 and 16 if devices are available. Record the LaunchBox version and target SDK from an authorized APK inspection ([doc 03 plan](03-LAUNCHBOX-INTEGRATION.md#authorized-reproducible-apk-inspection-plan-not-performed)). Check `PackageManager` logcat for "Intent does not match component's intent filter".
6. Record Dispatch to the Target App separately from a human-observed Launch.

## Unverified

- What LaunchBox actually emits across versions: scheme, MIME, category, flags and ClipData. Also whether `{file.uri}` depends on the scoped storage setting.
- Whether LaunchBox accepts a command without `-n`, or with `-t`, and how it resolves an implicit intent. These would only matter for option (c).
- Whether any other undocumented placeholders exist on Android.
- How the per-platform default and the per-game override take precedence in current builds.
- Every Android 14–16 outcome. Only Android 13 on the Odin has historical observations.
